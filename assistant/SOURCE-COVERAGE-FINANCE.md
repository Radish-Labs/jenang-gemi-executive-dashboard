# Finance and partner read source coverage

This package supplies **43 source-reviewed table mappings**: 26 existing mappings with corrected provenance/semantics or missing safe fields, and 17 new safe projections. It adds no database mutation, upstream refresh, credential, scope, or payment behavior. Runtime source availability must still be checked by the central reader; no hosted query or deployment was performed by this implementation task.

## Confirmed runtime hole

`partner_order_payments` belongs to **analytics**, not the partner database. `api/partner-sales/index.php` sets `$paymentPdo = analyticsDb()` before reading and preparing the payment ledger, and labels its settlement source `analytics.partner_order_payments`. Orders and weekly bills remain in the partner database. The catalog fixes the connection mapping rather than swallowing a missing-table error. The app's interactive endpoint also synchronizes confirmed payments and prepares schema; the MCP reader must only select the existing ledger and must not invoke that endpoint or those preparation routines.

## Canonical computed views still required at integration

The generic catalog now identifies these inputs, but it does not claim computed-report parity. Use the existing canonical implementations or the already prepared passive services on `assistant-comprehensive-coverage`; do not invoke dashboard GET handlers that prepare schemas, refresh state or synchronize payments.

- **Monthly P&L and recipient allocation:** the current `assistant/lib/monthly-profit.php` is already the owner/finance/recipient-checked path. Client discovery must expose it before claiming callable coverage. It combines actual sales, SKU costs, manual inputs, accounting and saved monthly/yearly allocation rules; never sum `profit_loss_entries` or infer allocation from yearly pool percentages.
- **Accounting/cash overview:** `jg_accounting_summary`, `jg_accounting_cash_flow_report`, `jg_accounting_cash_history`, `jg_accounting_monthly_summary`, `jg_accounting_purchase_order_outflow`, automatic cash readers and partner receivable totals need the existing passive service extraction/strict failures. The earlier local branch has `assistant/lib/accounting-overview-metrics.php` and `cash-metrics.php` plus canonical `accounting-overview-service.php`; do not cherry-pick writes/scopes alongside them. Current balance and selected-month movement have different meanings.
- **Wallet calculations:** `api/wallet/index.php::jg_wallet_summary` uses anchors, platform transactions, marketplace order totals and manual releases. The earlier passive `wallet-metrics.php` avoids interactive sync/setup paths. Missing provider history must remain unknown, and unknown wallet balances must not silently become zero.
- **Partner receivables and stock deposits:** apply the canonical saved bill/payment/status logic with cross-database snapshot limitations. `partner_order_payments` now reads correctly, but a generic aggregate cannot deduplicate weekly-bill receipts and accounting cash.
- **Remaining typed configuration projections:** `partner_profiles.selected_skus_json`/`pricing_json`, P&L product-card/SKU membership/layout JSON, accounting category guidance prose, accounting presentation preferences and saved legacy P&L file data require bounded typed projection. Arbitrary raw JSON is intentionally not enabled. Monthly named-recipient allocation is already a protected semantic tool, not an unguarded configuration table.

## Deliberately excluded data

Authentication/reset fields in partner profiles, private customer/contact identifiers, tax IDs, free-text notes and proof/receipt contents, raw provider or audit JSON and internal migration tables are excluded. These exclusions are distinct from missing safe business mappings. Profile/favicons and other binary branding assets are presentation media rather than numeric finance source data. Current grants are not changed. Wallet account-bearing tables declare the central configured-account row filter. Timestamp timezone metadata is explicit: reviewed UTC-written P&L/run bookkeeping fields are UTC; other legacy or database-default times remain unknown until their timezone is verified, preventing automatic seven-hour shifts.

## Validation

`assistant/tests/finance-source-catalog.php` runs offline against the actual app DDL and connection call sites. It verifies every column and source, accepted types/order keys, protected-field exclusions, analytics settlement binding, decimal-money types, allocation protection, display-versus-value descriptions, category discovery and canonical expense join/date predicates. It does not contact production, load database configuration, create tables or run migrations.

Root integration must additionally test merged registry queries, account/brand/partner row constraints, unavailable/empty distinctions, pagination, query limits and hosted availability. No new source has been declared live solely because its schema exists in this repository.
